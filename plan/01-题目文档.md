## 一、项目介绍

**痛点**：一个人的钱同时躺在微信、支付宝、银行卡三本账单里。同一笔消费可能既记在银行卡（扣款）又记在支付平台（渠道明细），**合并后看起来花了两次**；而"本人转账""退款""AA 回款""报销"这四类进进出出的钱，金额与真实消费一模一样，**按流水求和必然把支出算虚高**。现有记账工具要么是"合并 + 饼图"（把你导入的多份账单简单堆在一张图上），要么是账本应用（要你手工记账），**没有一个能把同一笔消费跨平台认出来并扣掉、把转账语义认出来并排除**。

**需求原话证据（✅ 直连取证）**：`Tony-Liu217/FlowLens`（2026-10-08 建仓）README 原文——"同一笔消费可能同时出现在银行卡和支付平台账单中，本人转账、退款、AA 回款和报销也会影响对个人支出的理解"。这句话把本题的四个核心判定（**跨平台去重、转账识别、退款识别、AA 回款识别**）逐条点明，是需求真实性的直接文本证据。

**本题据此划清界限**：**不触碰任何平台加密数据库、不做密钥提取/内存 dump**；**只解析用户通过官方自助功能导出的账单文件**——微信：我-服务-钱包-账单-常见问题-下载账单；支付宝：账单-开具交易流水证明。这条区分必须写清：**聊天记录导出 = 触碰平台加密库（已判违规）；官方自助导出的账单文件 = 用户自己下载的文本/表格（本题范围）**。合规风险低，且这是本题与已删库方向的本质区别。

- 银行：PDF / Excel（**模板无穷**，见扩展项与边界）；

- 中文分词（可选，非首期）：`wangfenjin/simple`（**870★**，SQLite FTS5 中文 tokenizer）——用于商户名相似度辅助，首期只做规则归并，不引入分词依赖。

## 二、任务要求

> 首期范围限定为**五个模块**（对应 M1–M5，见 plan/00 里程碑）；银行 PDF、OCR 长截图、多币种、可选 MCP 均列扩展项。每模块写清**输入 / 输出 / 确定性纪律**。

### 模块① 多平台账单导入（微信 ZIP / 支付宝 CSV / 银行 CSV+Excel）

- **输入**：用户通过官方自助功能导出的账单文件——
  - 微信：带密码 ZIP（用户自行解密后）→ CSV/XLSX；
  - 支付宝：官方导出 CSV（**GBK/GB18030**，含表头广告行）；
  - 银行：CSV + Excel（首期仅此两种；**PDF 列扩展项**）。
- **输出**：统一中间表示（每笔流水：来源平台 / 交易时间 / 金额 / 收/支方向 / 对手方 / 商品说明 / 原始行号）。
- **确定性纪律**：
  - 编码与表头漂移的**确定性解析**——编码白名单（GBK/GB18030/UTF-8，**显式声明探测顺序**，探测失败报错不猜测）；
  - 支付宝导出**表头广告行**（导出文件顶部若干行是平台说明文字，非表头）按"定位真实表头行"的确定性规则剥离，剥离失败 → 三态 `invalid` 并列出；
  - 列名漂移按**列名白名单 + 别名映射表**处理，未登记列名记 `unknown`（行仍可用），列对齐不可信的行 **不入库**（宁可少一行，不可把错位的值当对的）；
  - 千分位、货币符号、收支分列（收入列/支出列 vs 单列带正负号）按显式规则解析，非数值一律 `invalid` 并列清单，**不静默跳过**；
  - 三态 `ok` / `invalid` / `unknown` 落测试。

### 模块② 商户名归一化（同一商户在不同平台的不同写法归并）

- **输入**：模块① 产出的统一流水（对手方字段）。
- **输出**：归一化商户名 + 归一化映射台账（原名 → 规范名 + 归并依据）。
- **确定性纪律**：
  - **规则归并**（去空格/全半角统一/后缀剥离如"有限公司/有限"/别名表），**不做模糊语义猜测**；
  - 归并动作**必须可观测**：每一条归并都挂"依据"（命中哪条规则/哪条别名），未命中规则的原样保留；
  - 别名表是**冻结产物**（程序化生成 + 位级守门），禁手改——商户名归一化一旦可手改，"引擎对不对"就永远无法与"数据对不对"分离。

### 模块③ 跨平台去重（金额 + 时间窗口 + 对手方三元组聚类）

- **输入**：模块② 归一化后的多平台流水。
- **输出**：去重簇清单（每簇含成员流水、判定依据、簇内代表笔）+ 去重后净流水。
- **确定性纪律**：
  - 判定键 = **金额 + 时间窗口 + 对手方**三元组；**时间窗口为用户可配置参数**（默认值标注"经验默认，非官方"）；
  - 聚类规则确定且**可复现**（同输入 → 同簇划分，无随机性）；簇划分排序规则显式声明；
  - **"看起来像重复"与"判定为重复"必须可区分**：三元组命中记候选簇，是否合并须过**跨平台前提**（不同平台才算跨平台重复；同平台同金额同时刻的重复须另立依据），**判定结果逐簇挂依据**；
  - 去重**不改变原始流水**——净流水是"原始流水 + 去重标记"的视图，原始件永远保留（账单是审计凭证）。

### 模块④ 转账 / 退款 / AA 回款语义识别（关键词表 + 规则）

- **输入**：模块② 归一化后的流水（对手方、商品说明、收支方向）。
- **输出**：每笔流水的**语义标签**（`消费` / `本人转账` / `退款` / `AA回款` / `报销` / `未知`）+ 判定依据（命中关键词/规则）。
- **确定性纪律**：
  - **关键词表 + 规则**（如"转账/零钱通/还款/退款/原路退回"等词面 + 收支方向组合），词表是**冻结产物**（程序化生成 + 位级守门）；
  - **"未知"是一等结论**——不猜、不默认归入"消费"；未命中任何规则的流水记 `未知` 并在报告中显式列出，绝不静默当作消费（那会让"真实支出"虚高）；
  - 关键词表**一处定义、多处引用**（识别引擎、报告、基准全部引用同一份词表）；
  - **不做自由文本语义硬判**——只做"词面命中 + 方向组合"的确定性判定，语义模糊情形落 `未知`。

### 模块⑤ 周期性订阅识别与报告（本地 HTML 报告）

- **输入**：模块③④ 产出的净流水 + 语义标签。
- **输出**：
  - **周期性订阅清单**（按**商户 + 金额 + 日期**聚类找固定周期：月/季/年；**涨价追踪**：同商户同周期金额发生变化时列出变动）；
  - **本地 HTML 报告**（单文件、零外部依赖、零 CDN）：真实支出汇总 + 去重簇明细 + 语义标签分布 + 订阅清单 + 涨价记录。
- **确定性纪律**：
  - 周期判定 = **商户 + 金额 + 日期间隔**的规则判定；周期参数（最小重复次数、间隔容差）**用户可配置**，默认值标注"经验默认，非官方"；
  - 涨价追踪只输出**观测到的变动**（前后金额 + 日期），**不做"预测涨价"类模糊输出**；
  - HTML 报告**单文件内联**（无 CDN、无外链、无遥测）；报告生成确定（同输入 → 同报告字节，配位级守门）；
  - **报告只呈现引擎结论**，不做二次计算（避免"报告里长出第二份口径"）。

### 扩展项（首期不做，不承诺交付）

- **银行 PDF 账单解析**：**模板无穷**（各家银行、各版本排版不同），**只声明覆盖度、不承诺 100%**；用合成/示例模板兜底，缺模板的 PDF 落 `unknown` 并列清单。**不进首期 DoD**。
- **OCR 长截图**：微信/支付宝"账单长截图"识别。依赖 OCR 引擎，与"纯本地零第三方依赖"内核冲突，列扩展项。
- **多币种**：汇率换算依赖外部汇率源（联网）或手工维护汇率表，列扩展项。
- **可选 MCP 接口**：把对账能力暴露为 MCP 工具供本地 agent 调用。**可选、非首期**。

## 六、边界与非目标

- **不做任何平台数据库解密 / 密钥提取**（**最重要红线**）：
  - **只解析用户通过官方自助功能导出的账单文件**——微信：我-服务-钱包-账单-常见问题-下载账单；支付宝：账单-开具交易流水证明；
  - **不触碰平台加密数据库、不做内存 dump、不做密钥提取**；
  - **与聊天记录导出方向的法律区别必须写清**：聊天记录导出（PyWxDump / chatlog）触碰平台加密数据库，已被法律清除（2025-10-20，两仓库均已移除）；**官方自助导出的账单文件是用户自己下载的文本/表格**，本题范围合规风险低；
